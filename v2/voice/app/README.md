# 음성 주문 데모 (2단계)

노트북 하나에서 인터넷 없이 돌아가는 음성 주문 앱이다. 한 턴은 이렇게 처리된다:

1. **STT**: faster-whisper medium int8(CPU, 한국어 고정)이 말을 글로 바꾼다.
2. **두뇌**: `song/gemma4-26b-cafe-64e`(v1 64e 전체 빌드)가 도구를 고른다. 기본은 **CPU 전용**이다.
3. **답**: 짧은 템플릿(`replies.json`)으로 만든다. 메뉴 안내와 주문 내역은 `menu.json`과 주문 상태에서 바로 만든다.
4. **말 다듬기**: 모든 답은 `tts_text.normalize()`를 거친다(1잔 → 한 잔, 샷 -0.5 → 반 샷, 번호·괄호 제거).
5. **TTS**: Supertonic 3 int8(기본 여성 sid 0, 4단계)이 읽는다. Windows Heami로 바꿀 수 있다. 같은 문장은 다시 합성하지 않는다.

## 실행과 종료

```
powershell -ExecutionPolicy Bypass -File v2\voice\app\start_demo.ps1 -Open
powershell -ExecutionPolicy Bypass -File v2\scripts\stop_ollama.ps1        # Ollama만 따로 끌 때
```

- **Ollama 시작:** `start_ollama.ps1`로 띄운다. 서버 프로세스에만 `OLLAMA_IGPU_ENABLE=1`, `LLAMA_ARG_CACHE_RAM=0`, `OLLAMA_NOPRUNE=1`을 주고, 로그로 NOPRUNE를 확인한다. 이미 떠 있는 서버를 쓰려면 `-UseRunning`을 붙인다.
- **준비:** 프롬프트가 바뀐 뒤 첫 실행은 앞부분(약 4.4k 토큰)을 CPU에서 처음부터 계산하느라 2–4분 걸린다. 그다음부터는 약 40초.
- **전원:** 배터리로 돌리면 CPU가 느려져 프롬프트 처리가 10배 넘게 느려진다(11-25 측정: 48 → 3.6 토큰/초). 충전기를 꽂고 쓴다.
- **종료:** Ctrl+C나 앱 종료 시 이 스크립트가 띄운 Ollama를 `stop_ollama.ps1`로 끄고, 프로세스와 포트가 닫혔는지 확인한다.
- **서버 옵션:** `-AppArgs`로 넘긴다. 예: `-AppArgs "--layout compact --a3 prompt"`.

| 옵션 | 기본 | 뜻 |
|---|---|---|
| `--config` | `demo` | 데모 프롬프트와 도구(아래). `v1`은 실험 프롬프트·도구 그대로 |
| `--mode` | `cpu` | CPU 전용(`num_gpu 0`). `igpu`는 iGPU |
| `--num-ctx` | 8192 | 4096은 쓰지 말 것(프롬프트가 잘린다) |
| `--layout` | `append` | `append` = 지난 턴을 뒤에 붙이기만 한다. `compact` = 고정 앞부분 + 최근 2번 주고받은 말(+ 로봇의 마지막 질문) + 주문 상태 + 새 말. `deploy` = v1 배치 |
| `--a3` | `app` | 온도 묻기를 앱이 한다(`app`). `prompt` = 데모 프롬프트 규칙 + 앱 |
| `--history` | `tools` | 지난 턴을 도구 호출 형식으로 기록 |
| `--max-turns` / `--trim-to` | 20 / 10 | append에서 지난 턴이 20개를 넘으면 최근 10개만 남긴다 |

## 주문 흐름 (A1, A2)

주문 단계는 `주문 중 → 확인 대기 → 확정`이다. 화면의 주문 내역 위에 "⏳ 확인 대기 · 매장/포장 미정"이나 "✅ 주문 확정 · 포장 (변경은 직원)"이 보인다.

- **확인 대기:** 모델이 confirm_order를 부르거나 손님이 "아니 없어요", "이게 다예요", "주문할게요"처럼 끝났다고만 말하면, 바로 확정하지 않는다. 주문을 한 문장으로 읽고, 매장/포장을 모르면 묻는다.
  - 예: "아이스 아메리카노 한 잔, 바닐라라떼 한 잔이요. 드시고 가세요, 포장이세요?"
  - 포장을 이미 말했으면: "… 포장으로 주문할까요?"
- **확정:** 확인 대기에서 손님이 "네", "포장이요", "먹고 갈게요"처럼 분명히 답하면 확정한다. 매장/포장을 모르는 채로 "네"만 하면 매장/포장을 다시 묻는다.
- **바꾸기:** 확인 대기에서 메뉴를 바꾸거나 더하면 그대로 적용하고 다시 `주문 중`이 된다.
- **확정 뒤:** 더하기·바꾸기·빼기는 적용하지 않는다. "주문이 이미 들어갔어요. 변경은 직원 불러 드릴게요."라고 말하고 직원을 부른다. "새 손님"을 누르면 모두 지운다.
- **모델에게 주는 정보:** 확인 대기와 확정 단계에서는 `[현재 주문 내역]` 메시지 끝에 단계 줄이 붙는다. 주문 중에는 아무것도 붙지 않아, 시험 문항의 입력은 전과 같다.
- **모델 없이 처리하는 짧은 답 (`flow.py`):** 말 전체가 "네 / 포장이요 / 아니요 / 이게 다예요" 같은 말뿐일 때만 모델을 부르지 않는다. "네, 그리고 라떼 하나 더요"처럼 섞이면 모델로 간다.
- **매장/포장:** 손님이 그 세션에서 한 말(포장, 테이크아웃, 가져갈게요, 먹고 갈게요, 매장 등)로 정한다. 모델의 dine_option은 "takeout"일 때만 믿는다(모델은 말이 없으면 dine_in을 넣기 때문).

## 온도 묻기 (A3)

따뜻한 것과 아이스가 둘 다 되는 메뉴(아메리카노, 콜드브루, 라떼 종류, 차)를 온도 없이 주문하면 "따뜻한 거요, 아이스요?"라고 묻는다. 에이드(아이스만), 에스프레소(따뜻하게만), 디저트는 묻지 않는다.

- **기본(`--a3 app`):** 모델은 v1 문구 그대로다. 앱이 온도 없는 add_item을 담지 않고 묻는다.
  - 이때 대화 기록에는 add_item 대신 그 질문(ask_clarification)이 남는다.
  - 손님이 온도를 말했는지는 이번 말과, 로봇이 바로 앞에서 질문했을 때의 앞 말에서 찾는다(따뜻, 뜨거, 아이스, 차가운, 아아, 뜨아, 아바라 등).
- **`--a3 prompt`:** 데모 프롬프트에 `[온도 묻기]` 규칙을 넣는다. 함께 바꾸는 것: v1 기본값 문구("온도: 따뜻하게"), 메뉴판의 "(기본 따뜻한)", add_item의 온도 설명. 앱 안전장치도 그대로 켜져 있다.
  - 기본이 아닌 이유: 회귀 시험에서 온도와 상관없는 문항까지 8개가 틀렸다(아래). 실제 세션 다시 돌리기에서도 규칙만으로는 "라떼 반샷만 해서 주세요"를 묻지 않고 따뜻하게 담았다.

## 주문 내역 읽기 (B1)

- **`read_order` 도구:** 손님이 무엇을 시켰는지 물으면 모델이 부른다. 앱이 주문 상태에서 읽는다. 예: "지금 아이스 바닐라라떼 반 샷 덜 달게 한 잔이에요."
- **모델이 쓴 목록:** 모델이 "[현재 주문 내역] 1. …"처럼 글로 목록을 쓰면 읽지 않고, 같은 방식으로 주문 상태에서 읽는다(kind `free_text_replaced`).
- **옵션 질문:** "당도가 어느 정도예요?"처럼 옵션 자체를 물으면 inform이 옵션 설명을 한다(`replies.json`의 `inform.option_detail`).

## 데모 설정 (`demo/`, 앱에서만 사용)

v1 실험 파일(`cafe_common.py`, `data/tools.json`, `data/menu.json`)은 그대로 두고, 앱에서만 쓰는 설정을 따로 만들었다.

- **`demo/rules.txt`:** v1 시스템 프롬프트의 `[메뉴판]` 바로 앞에 끼워 넣는 규칙이다.
  - inform 사용법
  - read_order 사용법
  - 온도 묻기(`--a3 prompt`일 때만)
  - 짧은 되묻기(한 문장, 고를 것은 최대 3개)
- **`demo/inform_tool.json`:** `inform(topic, item?)`. 답 문장은 `demo_config.inform_answer()`가 `menu.json`만 보고 만든다.
- **`demo/read_order_tool.json`:** `read_order()`, 인자 없음.
- **글 답 거르기:** 모델이 도구 없이 글로 답했는데 메뉴판에 없는 이름이 들어 있으면 읽지 않는다(`demo/common_cafe_items.json` + 메뉴처럼 보이는 단어). 로그에 `kind = free_text_blocked`로 남긴다.

## 답 문장 (`replies.json`, `tts_text.py`)

짧게 말한다. 문구는 `replies.json`에서 고치면 다음 턴부터 바로 반영된다.

| 상황 | 예 |
|---|---|
| 담기 | 네, 아이스 아메리카노 한 잔이요. (새 손님의 첫 메뉴에만 "더 필요하신 거 있으세요?") |
| 온도 묻기 | 따뜻한 거요, 아이스요? / 카페라떼는 따뜻한 거요, 아이스요? |
| 바꾸기 / 빼기 | 네, 샷 반만 넣을게요. / 네, 빼 드렸어요. (메뉴가 둘 이상이면 메뉴 이름을 붙인다) |
| 확인 대기 | 아이스 아메리카노 한 잔이요. 드시고 가세요, 포장이세요? |
| 확정 | 네, 주문 확인했어요. 금방 준비해 드릴게요. / 네, 포장으로 주문 확인했어요. … |
| 확정 뒤 변경 | 주문이 이미 들어갔어요. 변경은 직원 불러 드릴게요. |
| 주문 내역 | 지금 따뜻한 아메리카노 한 잔, 청포도에이드 덜 달게 한 잔이에요. |
| 메뉴 질문 | inform 답(menu.json) |

**말 다듬기 (`tts_text.normalize`, 모든 답에 적용):**

- **고유어 수:** 1–20은 고유어로 읽는다(1잔 → 한 잔, 3개 → 세 개, 20잔 → 스무 잔). 분·원처럼 한자어 수를 쓰는 말은 그대로 둔다.
- **샷:** shots_delta -0.5 → 반 샷, +1 → 한 샷 추가, -1 → 한 샷 빼고, 반샷 → 반 샷.
- **목록 표시:** `[제목]` 줄, 번호(1. 1) ①), 글머리(- * •), 괄호, `**` 같은 표시를 지운다.
- **화면:** 화면에도 다듬은 문장이 보인다.

## 화면

- **누르고 말하기:** 버튼이나 Space를 누르는 동안 녹음하고, 놓은 뒤 0.3초 더 녹음한다. 토글 모드도 있다.
- **끼어들기:** 로봇이 말하는 도중에 녹음을 시작하면 재생을 곧바로 멈춘다.
- **마이크:** 녹음할 때만 열고 바로 놓는다.
- **주문 단계:** 주문 내역 위에 확인 대기 / 확정 표시가 보인다. 답에는 종류 표시가 붙는다(주문 확인 질문, 매장/포장 질문, 주문 내역, 메뉴 안내 등).

## 확인 결과 (2026-11-25, CPU 전용, 충전기 연결)

### 실제 세션 f68fd4 다시 돌리기 (15턴, `replay_summary.py` → `v2/voice/results/replay_f68fd4.md`)

로그의 인식 결과 15개를 같은 순서로 글자로 넣었다(`run_script.py --from-log f68fd4`, 로그는 커밋하지 않는다). 턴별 표는 `app_script_replay_*.md`에 있다.

| 실행 | llm_s 중앙값 | prompt_s | gen_s | 새로 계산한 토큰 | total_s |
|---|---:|---:|---:|---:|---:|
| 전 (11-24 코드) | 8.47 | 5.81 | 2.34 | 171 | 9.50 |
| **후 (기본: append, A3=app)** | **7.64** | 5.50 | 1.95 | 182 | **8.50** |
| 후, compact(D1), A3=prompt | 9.68 | 8.22 | 3.61 | 256 | 10.97 |

- **전:** 둘째 말("안녕 없어요", STT 오류)에 주문을 바로 확정했고, 그 뒤에도 주문이 계속 바뀌었다. 13, 15번째 턴에는 모델이 쓴 목록("[현재 주문 내역] 1. … 1잔")을 그대로 읽었다.
- **후 (기본):**
  - 둘째 말에 주문을 읽고 매장/포장을 물었다(확인 대기).
  - "라떼 반셈만 해서 주세요"에 "따뜻한 거요, 아이스요?"라고 물었다.
  - 주문 내역 질문에는 read_order로 주문 상태를 읽었다.
  - 마지막 주문은 따뜻한 아메리카노 / 청포도에이드 덜 달게 / 아이스 바닐라라떼 반 샷 덜 달게였다. 손님이 말한 대로다.
- **알려진 실수:** "따뜻하기라고 말한 적 없는데 … 바닐라라떼"에서는 "따뜻"이 있어 온도를 말한 것으로 보고, 따뜻하게 담았다(부정은 알아듣지 못함). 다음 턴에 손님이 "아이스로"라고 해서 고쳐졌다.

### 속도: 왜 compact(D1)를 기본으로 하지 않았나

llama-server는 앞부분이 같으면 다시 계산하지 않는다. compact는 매 턴 최근 대화 창이 밀리므로, 고정 앞부분 뒤의 모든 것(창 + 주문 상태 + 새 말)을 매 턴 다시 계산한다. append는 지난 턴에 새로 붙은 것만 계산한다.

CPU에서는 새로 계산하는 토큰 하나가 약 25–33 ms라서, compact가 턴당 약 75토큰 더 계산하고 약 2초 느렸다.

전체 길이가 짧아지는 이점(생성 속도, 체크포인트 메모리)보다 이 비용이 컸다. compact는 `--layout compact`로 남겨 두었다.

### 고정 앞부분 토큰 (`prefix_breakdown.py` → `v2/voice/results/prefix_breakdown.md`)

| 부분 | 토큰 |
|---|---:|
| 기본 규칙(v1 프롬프트) | 1048 |
| 데모 규칙(rules.txt, `--a3 prompt` 기준) | 582 |
| 메뉴판 | 810 |
| 메뉴 규칙 + 줄임말 | 564 |
| 도구 정의 8개 | 1439 |
| 합계(빈 주문 + 한 마디 포함) | 4480 |

앞부분은 한 번 계산해 두면 다시 계산하지 않는다. 그래서 줄여도 턴마다 빨라지는 양은 작다(문맥이 짧아져 생성이 조금 빨라지는 정도). 대신 프롬프트를 바꾼 뒤 첫 준비 시간이 줄어든다.

줄일 만한 곳(아직 적용하지 않음):

- 도구 설명의 긴 영어 문장 줄이기(add_item 455토큰).
- 메뉴판 줄을 표 형식으로 압축하기(줄마다 약 50토큰).
- v1 규칙과 데모 규칙에서 겹치는 inform 안내 줄이기.

### 속도 목표 (글자 4초, 음성 6초 이하): 못 미침

| 단계 | 지금 (중앙값) | 막는 것 |
|---|---:|---|
| 프롬프트 처리 | 약 5.5 s | CPU에서 새 토큰 하나가 25–33 ms다. 턴마다 지난 답 + 주문 상태 + 새 말로 약 150–200토큰이 새로 생긴다. |
| 생성 | 약 2 s | 생성 토큰 하나가 65–100 ms이고, 도구 호출 하나가 약 20–25토큰이다. 문맥이 6k를 넘으면 더 느려진다. |
| TTS | 약 1 s | 처음 듣는 문장만. 같은 문장은 캐시에서 바로 나온다. |
| STT | 약 3.1–3.6 s | whisper medium은 짧은 말도 30초 창을 계산한다. |
| 합계 | 글자 8.5 s, 음성 약 10.7 s | |

  - 모델 없이 처리하는 확인 답: 약 1초.
  - 같은 문장 TTS 캐시.

## 알려진 한계

- **속도:** 위 표 참고. 글자 한 턴 약 8.5초, 음성 약 10.7초.
- **온도 말 찾기:** 단어 기반이다. "따뜻하게라고 말한 적 없는데"도 온도를 말한 것으로 본다.
- **"질문" 판정:** 11-25 마지막 측정 뒤에 고쳤고, 다시 측정하지 않았다. 지금은 "더 필요하신 거 있으세요?"를 질문으로 치지 않는다. 고치기 전에는 이 말 바로 앞의 "아이스"를 다음 메뉴의 온도로 보고, 자체 시험에서 "카페라떼로 주세요"를 묻지 않고 따뜻하게 담았다.
- **수량 중복(모델 약점, 앱에서 고치지 않음):** 같은 메뉴를 1잔과 2잔으로 따로 담은 적이 있다.
- **STT 오류:** 메뉴 밖 단어는 잘못 알아듣기 쉽다(11-25 자체 시험: "캐리어" → "페리얼").
- **세션:** 메모리에만 있다.
