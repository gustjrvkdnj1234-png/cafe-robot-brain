# 블로그 재료: 카페 알바 로봇의 언어 두뇌

블로그 글을 쓸 때 이 파일 하나만 보면 되도록 모았다. 숫자는 모두 아래 적은 파일에서 그대로 옮겼다. 표나 숫자를 글에 쓸 때는 괄호 안의 파일을 출처로 확인하면 된다.

- 기계: 노트북 1대(Intel Core Ultra 7 255H, RAM 32 GB, Arc 140T 내장 GPU), Windows 11, Ollama 0.40.15
- 공통 조건: thinking 끔, temperature 0, seed 42, num_ctx 8192, 같은 시스템 프롬프트와 도구 6개
- 공식 점수는 **엄격 채점의 정답(exact) 비율**이다. 관대 채점은 보조 지표다.

## 2. 핵심 발견 (중요한 순서)

**1. 속도를 가장 크게 바꾼 것은 모델이 아니라 프롬프트 배치였다.**
- 주문 내역이 바뀐 주문: 64개 CPU 73.2 s → 4.68 s, 48개 CPU 73.6 s → 4.54 s. 첫 토큰은 71.2 s → 2.27 s(약 30배).
- 원인: Ollama(gemma4 렌더러)는 도구 설명(약 1,100토큰)을 시스템 프롬프트 **뒤에** 붙인다. 시스템 프롬프트 끝의 주문 내역이 바뀌면 2,362토큰에서 갈라져 도구 설명까지 다시 계산한다. 보통 SWA 캐시에서는 그 앞에 체크포인트가 없어 프롬프트 전체(약 3,500토큰)를 다시 계산했다(로그의 ‘forcing full prompt re-processing’ 16번). 배포용 배치는 3,469토큰까지 같아 재계산이 0번이었다.
- 출처: `results/step6/latency.md`(6a ‘시스템 프롬프트 재사용’, 6b 해석 4, 6c), `results/step6/deploy_interpretation.md`.

**2. 전문가를 절반(64개)으로 줄여도 카페 일은 한다.**
- 카페 93.3%(원본 94.2%), 실전 70.0%(원본 75.0%, 차이 1문항 L14). 64개 vs 원본 McNemar p = 1.000.
- 크기 18 GB → 11 GB(`ollama list`), CPU 정상 상태 메모리 20.2 → 13.4 GB. 원본은 iGPU에 안 들어가지만 64개는 100% iGPU로 돈다.
- 출처: `results/step5/comparison.md`, `results/step5/keep64_interpretation.md`, `results/step6/latency.md`.

**3. 가지치기는 일반 지식부터 버린다. imatrix 탓이 아니다.**
- 지식: 대조군 73.7% → 98개 58.3% → 64개 47.3% → 48개 38.3%(무조건 D 30.0%).
- 원본(imatrix 있음)과 대조군(없음)은 카페 94.2/94.2, 실전 75.0/75.0, 지식 72.7/73.7로 같다. 지식 문항 차이 15개(대조군이 나은 것 9, 못한 것 6)로 잡음 수준.
- 카페 문장으로 전문가를 골랐으니 예상한 결과다(98개의 ‘잃는 기여’ 0.2%).
- 출처: `results/step5/comparison_notes.md` 1번, `results/step5/keep98_interpretation.md`.

**4. 무너지는 순서가 있다: 일반 지식 → 사람이 쓴 실전 문장 → 정형화된 카페 문장.**
- 실전은 98·64개에서 1문항(L14)만 잃다가 48개에서 5문항(L09, L13, L14, L16, L20)을 잃는다(75 → 50%). 카페는 48개도 93.3%.
- 카페 보정 문장으로 한 은닉 상태 검증(다음 토큰 1순위 일치)은 98개 92.7%, 64개 80.3%, 48개 76.8%로 조금씩만 나빠져, 48개의 실전 붕괴를 예고하지 못했다.
- 교훈: 보정 데이터와 비슷한 시험만 보면 가지치기가 안전해 보인다. 사람이 따로 쓴 시험이 필요하다.
- 출처: `results/step5/comparison_notes.md` 2번, `results/step5/keep48_interpretation.md`.

**5. 같은 하드웨어에서는 가지치기가 속도를 거의 바꾸지 않는다. 얻는 것은 ‘iGPU에 들어간다’다.**
- CPU 생성 속도 원본·98·64·48개 13.7~15.0 tok/s, 주문 1건 중앙값 3.09~3.43 s.
- 64개 iGPU 2.55 s / 최대 8.5 s vs CPU 3.16 s / 30.2 s.
- 12b는 밀집 모델이라 26b MoE보다 느리다(CPU 9.8 vs 15.0 tok/s).
- 출처: `results/step6/latency.md` 6a 해석 3.

**6. 16 GB 노트북에는 ‘텍스트 전용 + CPU’ 48개가 들어가고, 64개는 아슬아슬하다.**
- 48개 CPU 6b: 정상 상태 8.4 GB, OS 포함 13.2 GB, 여유 2.8 GB. 64개 CPU 6b: 14.9 GB, 여유 1.1 GB.
- 단 6b만 쓰면 주문 내역이 바뀔 때 71 s가 걸린다. 6c 배치와 함께 써야 쓸 만하다.
- 출처: `results/step6/latency.md` 6b, `results/step6/lean_interpretation.md`.

**7. 3·5단계의 ‘가끔 아주 느림’과 메모리 부족은 llama-server 프롬프트 캐시 때문이었다.**
- 3단계 원본 26b CPU: 주문 최대 81 s, 30 s 넘은 카페 문항 8개. 지식 시험 중 가용 RAM 0.04 GB, 페이지 파일 +1.9 GB(98개).
- 캐시(최대 8 GB)를 끄자 같은 CPU에서 최대 27.5 s, 메모리 변화 ±0.2 GB.
- 그래서 비교 화면(7단계)과 이 글의 시간·메모리는 6a 값을 쓴다.
- 출처: `results/step6/latency.md` 6a 해석 1, `results/step5/keep98_interpretation.md`.

**8. REAP 점수에는 사각지대가 있다(4층).** → 3장 일화 5.

**9. 작은 모델은 거절 이유를 ‘불가능’으로 뭉뚱그린다.**
- 이유 코드만 틀린 문항 5건(e4b 2, 12b 2, 48개 1)이 모두 ‘불가능’을 골랐다(정답은 ‘메뉴에 없음’ 4, ‘애매함’ 1). 원본·대조군·98·64개는 0건.

### 일화 5. REAP 점수만 믿으면 4층이 망가진다 (`results/step4/reap_summary.md` 4-2, 5)

- REAP 점수는 ‘쓰일 때의 평균(게이트 × 출력 노름)’이라, 얼마나 **자주** 쓰이는지를 반영하지 않는다.
- 4층에는 토큰의 32~70%가 거쳐 가는 ‘바쁜 전문가’ 8개가 있다(119번 70%, 23번 69%, 55번 69%, 74번 67%, 27번 64%, 1번 62%, 47번 44%, 54번 32%). 한 번에 내는 출력(노름 1.5~2.0)이 작아 REAP 순위는 하위권이다(5개가 128개 중 112~117위).
- 순수 REAP로 98개만 남기면 이 8개가 모두 잘린다. 잃는 REAP 점수는 4.7%뿐이지만 잃는 기여는 23.1%이고, 라우팅 배정의 67.3%가 다른 전문가로 바뀐다.
- 그래서 실제 가지치기에서는 규칙 A(토큰 30% 이상이 거쳐 가는 전문가는 항상 남김)를 넣었다. 98개 계획 기준 재배정 토큰이 9.6% → 0.3%로 줄었다(`results/step5/prune_plans.md`).

## 4. 한계 (솔직하게)

1. **실전 시험이 20문항뿐이다.** 1문항이 5%p이고, McNemar 검정은 모든 비교에서 p ≥ 0.05다. ‘64개가 12b보다 낫다’, ‘98개와 64개가 같다’ 모두 방향만 보일 뿐 확정할 수 없다.
2. **카페 시험, 자판기, 보정 데이터, 시스템 프롬프트를 같은 AI 코딩 에이전트가 만들었다.** 자판기의 카페 95.0%는 그대로 믿기 어렵다. 보정 600문장은 시험과 겹치지 않게 걸렀지만(`scripts/check_overlap.py`) 같은 작성자의 문체라, 카페 시험은 가지치기 모델에 유리하다. 사람이 쓴 것은 실전 20문항과 그 정답뿐이다.
3. **실전 정답 중 일부는 해석의 여지가 있다**(L09 반샷의 방향).
4. **한 번씩만 돌렸다**(temperature 0, seed 42). 같은 설정에서도 T1-1(포장), D2-3(조건부)처럼 실행마다 바뀌는 문항이 있었다(6b·6c).
5. **16 GB 노트북은 실제로 재지 않았다.** 32 GB 기계의 측정값 + OS 4 GB 가정으로 어림했다. ‘Windows는 GPU 공유 메모리를 RAM의 절반까지 준다’도 확인하지 않은 가정이다.
6. **3·5단계 응답 시간은 공정하지 않다**(프롬프트 캐시, 모드 차이). 공정 비교는 6a의 30문항뿐이다.
7. **배포용 배치(6c)는 텍스트 전용 64·48개, 30문항으로만 확인했다.** 카페·실전 전체를 이 배치로 다시 채점하지 않았다.
8. **imatrix:** 원본은 Ollama의 비공개 C4 imatrix로 양자화됐다. 대조군으로 효과가 작음을 확인했지만, 카페 문장으로 만든 imatrix는 시험하지 않았다.
9. **가지치기는 모든 층에서 같은 수를 남겼다.** REAP 기준으로 위험해 보이는 가운데 층(7~9, 15~16)도 똑같이 잘랐다.
10. **지식 시험은 300문항 표본**이고 KMMLU 정답이 D에 쏠려 있다(무조건 D 30.0%).
11. **기계 1대, Ollama 0.40.15**의 동작(도구 설명 위치, SWA 체크포인트)에 기대는 결과가 있다. 다른 런타임에서는 숫자가 달라질 수 있다.
12. **관대 채점은 보조 지표**다. 이유 코드가 실제 로봇 동작에 어떻게 쓰일지는 정하지 않았다.

## 6. 후속 아이디어

1. **실제 카페 데이터:** 실제 주문 녹취(또는 직원이 쓴 문장)로 실전 시험을 수백 문항으로 늘린다. 20문항의 통계 한계와 ‘같은 작성자’ 문제를 함께 푼다.
2. **48개는 왜 무너지나, 층별 예산:** 48개 실전 붕괴(5문항)가 어느 층에서 오는지 본다. REAP 손실이 큰 가운데 층(7~9, 15~16)은 더 남기고 앞쪽 층(0~4, 10, 14)은 더 자르는 식으로, 층마다 남기는 수를 다르게 해 같은 크기에서 점수를 비교한다.
3. **회복 미세조정:** 가지치기 후 카페 대화로 라우터나 LoRA를 짧게 학습해, 실전·지식 점수를 얼마나 되찾는지 본다.
4. **보정 데이터 비교:** 카페 보정 600문장 대신 (a) 일반 한국어 텍스트, (b) 카페 + 일반 혼합, (c) 사람이 쓴 문장으로 전문가를 골라 같은 시험을 본다. 카페 문장 imatrix로 다시 양자화하는 것도 함께.
5. **가중치 편집:** L14처럼 ‘시럽 규칙을 과하게 일반화’하는 실수를, 프롬프트가 아니라 가중치 편집(특정 전문가·뉴런 조정)으로 고칠 수 있는지 시험한다.
6. **온디바이스 / NPU:** Core Ultra의 NPU(OpenVINO 등)나 로봇용 보드에서 64·48개 텍스트 전용 모델을 돌려 전력·지연을 잰다. 16 GB 실기기 측정도 여기서 한다.
7. **배포용 배치로 전체 재채점:** 6c 배치로 카페 120 + 실전 20을 다시 돌려 점수 변화가 없는지 확정한다.
