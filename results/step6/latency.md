# 6a단계: 같은 조건에서 잰 응답 시간과 메모리

- 카페 시험 30문항(`data/exam_cafe.jsonl`의 4번째 줄마다, 12개 유형 모두 포함)을 한 번에 하나씩 차례로 보냄. thinking 끔, temperature 0, seed 42, num_ctx 8192, num_predict 512, 3·5단계와 같은 시스템 프롬프트와 도구.
- 모델마다: 모두 내림 → 시스템 프롬프트로 한 번 데우기(warm-up) → 모델을 올린 채 30문항. 실행: 2026-11-12, 같은 노트북(Core Ultra 7 255H, 32 GB, Arc 140T).
- **프롬프트 캐시 문제 해결:** `ollama serve`를 이 프로세스에만 `LLAMA_ARG_CACHE_RAM=0`(3·5단계에서 최대 8 GB까지 커지던 llama-server의 RAM 프롬프트 캐시를 끔)과 `LLAMA_ARG_SWA_FULL=1`(슬라이딩 윈도 층도 전체 길이 KV를 유지해서 앞부분을 다시 쓸 수 있게 함)로 띄웠다. 슬롯이 하나라 직전 요청의 KV가 그대로 남고, 같은 앞부분은 다시 계산하지 않는다.
- CPU 전용 = `num_gpu 0`(3단계와 같음). iGPU = `OLLAMA_IGPU_ENABLE=1`, `ollama ps`에서 100% GPU일 때만 잼.

## 시스템 프롬프트 재사용: 되는 경우와 안 되는 경우

- llama-server 로그로 확인했다. 시스템 프롬프트가 들어간 요청 348개(파일럿 포함) 중 291개는 앞부분 약 3,475 토큰을 그대로 썼고, 처음부터 계산한 것은 13개(모델을 올린 직후의 데우기)뿐이다.
- 나머지 44개는 앞 2,362 토큰만 다시 쓰고 약 1,100 토큰을 다시 계산했다. 이 문항들은 모두 **직전 요청과 ‘현재 주문 내역’이 다른 경우**였다(30문항 중 4개, 모든 모델에서 같은 문항).
- 이유: 주문 내역은 시스템 프롬프트의 맨 끝에 있지만, Ollama가 도구 설명(약 1,100 토큰)을 시스템 프롬프트 **뒤에** 붙인다. 그래서 주문 내역이 바뀌면 그 뒤의 도구 설명까지 다시 계산한다(2,362 토큰에서 갈라지는 것으로 보아 이렇게 추정한다).
- 실제 로봇에서는 손님이 하나를 담을 때마다 주문 내역이 바뀌므로, 두 번째 주문부터는 거의 매번 이 비용을 낸다. 프롬프트는 3·5단계 점수와 같은 조건을 유지하려고 바꾸지 않았다(`cafe_common.py`는 고정 파일). 아래 표는 두 경우를 나눠 적었다.

- 첫 토큰까지: 서버가 잰 (모델 로딩 + 프롬프트 처리 + 첫 토큰 생성 1번). 모델이 이미 올라가 있어 로딩은 0에 가깝다. Ollama는 도구 호출 하나를 다 만든 뒤에 내보내므로, 로봇이 실제로 움직이기 시작하는 시점은 ‘주문 1건 전체’에 가깝다.
- 주문 1건 전체: 요청을 보내고 응답을 다 받을 때까지(클라이언트에서 잼). 생성 토큰은 대부분 20~40개다.
- 정상 상태 메모리: 30문항을 처리하는 동안 2초마다 잰 값의 중앙값. CPU는 러너(llama-server) private 메모리, iGPU는 러너 private와 GPU 공유 메모리 중 큰 쪽(둘은 겹치므로 더하지 않음). 가중치 + KV 캐시(8,192 토큰, SWA 전체 길이) + 계산 버퍼 + 비전 프로젝터 + 초안(MTP) 모델이 들어 있다. 프롬프트 캐시를 껐으므로 시험 중에 늘지 않았다(아래 세부의 ‘메모리 변화’).
- 16 GB 노트북: OS·기본 프로그램 4 GB + 정상 상태 메모리(최댓값)로 어림했다. 여유 1.5 GB 미만이면 ‘아슬아슬’. 브라우저 등 다른 프로그램이 켜져 있으면 더 모자란다. iGPU의 GPU 공유 메모리도 같은 RAM에서 나오므로 계산은 같다. 다만 Windows는 GPU 공유 메모리를 보통 RAM의 절반까지만 주는 것으로 알려져 있어, 16 GB 노트북에서는 약 8 GB를 넘는 모델이 iGPU에 다 안 올라갈 수 있다(16 GB 기계에서 직접 확인한 것은 아님).

## 해석

**1. 프롬프트 캐시를 고치니 ‘가끔 아주 느린’ 문제가 대부분 사라졌다.**

- 3단계의 원본 26b(CPU)는 주문 1건 최대 81 s였다. 이번에는 같은 CPU에서 최대 27.5 s, 중앙값 3.09 s다(3단계 중앙값 3.43 s). 이제 느린 경우는 ‘주문 내역이 바뀐 경우’ 하나로 설명된다.
- 메모리는 시험 내내 거의 그대로였다(±0.2 GB). 3·5단계에서 지식 시험 중 가용 RAM이 0에 가깝게 떨어지던 것은 프롬프트 캐시 때문이었다.

**2. 남은 병목은 주문 내역이 바뀔 때 도구 설명 1,100 토큰을 다시 계산하는 것이다.**

- 앞부분을 다시 쓰면 첫 토큰까지 0.2~1.1 s인데, 주문 내역이 바뀌면 iGPU에서 1.8~8.8 s, CPU에서 8~42 s가 된다.
- 실제 로봇에서는 두 번째 주문부터 거의 매번 이 경우다. 그래서 ‘주문 내역이 바뀜’ 열이 실제 사용에 더 가까울 수 있다.
- 해결 방법(아직 하지 않음): 주문 내역을 시스템 프롬프트에서 빼서 도구 설명 뒤(예: 사용자 말 바로 앞의 별도 메시지)로 옮기면, 바뀌는 부분이 100토큰 정도로 줄어든다. 다만 프롬프트가 바뀌므로 카페·실전 점수를 다시 재야 한다.

**3. 같은 하드웨어로 비교하면, 가지치기는 속도를 거의 바꾸지 않고 메모리만 줄인다.**

- CPU에서 26b 원본·98·64·48개의 생성 속도는 13.7~15.0 tok/s, 주문 1건 중앙값은 3.1~3.4 s로 거의 같다. 토큰당 쓰는 전문가가 8개로 같아서 계산량이 같기 때문이다(5단계에서 추측한 것을 이번에 같은 CPU로 확인했다).
- 정상 상태 메모리는 CPU 기준 원본 20.2 GB → 98개 17.0 → 64개 13.4 → 48개 11.7 GB로 줄었다.
- iGPU에서는 가지치기 모델이 CPU보다 빠르다. 64개는 주문 1건 중앙값 2.55 s(CPU 3.16 s), 최대 8.5 s(CPU 30.2 s), 생성 20.4 tok/s(CPU 14.5)다. 원본 26b는 iGPU에 올라가지 않으므로, iGPU를 쓸 수 있게 된 것이 가지치기로 얻은 실제 속도 이득이다.
- 12b는 밀집 모델이라(토큰마다 12B 전부 계산) 26b MoE(토큰당 약 4B)보다 느리다. CPU 9.8 tok/s, iGPU 15.6 tok/s.

**4. 16 GB 노트북: 이 설정 그대로면 26b 계열은 어렵다.**

- 들어가는 것은 e4b(CPU·iGPU 모두)뿐이고, 아슬아슬한 것은 12b(CPU)와 48개(CPU)다. 64개는 CPU 기준 1.4 GB 부족하다.
- 이 메모리에는 8,192 토큰 전체 길이 SWA KV(재사용을 위해 켬), 비전 프로젝터, 초안(MTP) 모델이 들어 있다. 카페 로봇에 필요 없는 부분도 있다.
- 5단계 로딩 확인(SWA 전체 길이를 켜기 전)과 비교하면 SWA 전체 길이에 약 1.3 GB가 드는 것으로 보인다(48개 iGPU 러너 11.8 → 13.1 GB). 비전 프로젝터 제거, num_ctx 축소(프롬프트가 약 3,500 토큰이라 4,096은 빠듯함), KV 양자화 등으로 64개를 16 GB에 넣을 수 있을지는 아직 재지 않았다.
- 16 GB 노트북의 iGPU는 GPU 공유 메모리 한도(보통 RAM의 절반)가 있어, 여기서 잰 13~18 GB짜리 iGPU 설정은 그대로는 어렵다. CPU로 돌리는 것이 현실적이다.
