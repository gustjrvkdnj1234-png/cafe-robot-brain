## 6c 해석

- **주문 내역이 바뀌는 경우의 지연이 거의 사라졌다.** 첫 토큰까지 CPU 71 s → 2.3 s, iGPU 15.6 s → 4.8 s. 30문항 중 가장 느린 주문도 CPU 74~81 s → 6~7 s, iGPU 19 s → 9~10 s다. 로그에서도 배포용 배치 실행 중에는 ‘프롬프트 전체 재계산’이 한 번도 없었다(시험용 배치 6b에서는 16번).
- **앞부분을 다시 쓰는 평범한 주문은 조금 느려졌다.** CPU 0.89 → 0.98 s, iGPU 3.6 → 4.7 s. 이제는 바뀌는 부분이 늘 프롬프트 끝(3,469 토큰 이후)에 있어서, 매 요청마다 SWA 체크포인트를 되살리고 새로 만드는 일이 생기는 것으로 보인다. iGPU에서는 이 복사가 느리다. 그래도 두 경우의 차이가 사라져, 응답 시간이 고르게 되었다.
- **메모리:** 최댓값은 6b와 같다(64개 CPU 10.9 GB, 48개 CPU 9.2 GB). 중앙값은 0.7~0.8 GB 높아졌는데, 체크포인트(200 MiB)가 최대 개수인 4개로 유지되는 시간이 길어졌기 때문이다. 16 GB 노트북 판정은 바뀌지 않는다(64개 CPU 아슬아슬·여유 1.1 GB, 48개 CPU 여유 2.8 GB).
- **점수:** 내용이 달라진 문항은 2개(64개 iGPU T1-1 포장, 48개 iGPU D2-3 조건부)이고 둘 다 오답 → 정답이다. 두 문항 모두 5단계에서도 실행마다 흔들리던 문항이라, 배치 때문에 나아졌다고 보기는 어렵다. 나빠진 문항은 없다. 30문항뿐인 확인이므로, 배포용 배치를 실제로 쓰려면 카페·실전 시험 전체를 이 배치로 다시 재야 한다.

**에이전트 프롬프트 설계 팁:** 로컬 LLM은 직전 요청과 **앞에서부터 똑같은 부분**까지만 계산을 다시 쓴다. 그러니 프롬프트는 ‘절대 안 바뀌는 것 → 가끔 바뀌는 것 → 매번 바뀌는 것’ 순서로 쌓아야 한다. 역할·규칙·메뉴판 같은 고정 지시문과 도구 설명을 맨 앞에 두고, 주문 내역·시각·센서 값처럼 매 턴 바뀌는 상태는 맨 뒤, 사용자의 말 바로 앞에 둔다. 여기서 함정은 **도구 설명의 위치를 직접 정하지 못한다**는 점이다. Ollama(gemma4 렌더러)는 도구 설명을 시스템 프롬프트 뒤에 붙이므로, 시스템 프롬프트 끝에 넣은 상태 한 줄이 바뀌기만 해도 그 뒤의 도구 설명 1,100 토큰까지 다시 계산된다. 슬라이딩 윈도 어텐션 모델(Gemma 계열)은 갈라지는 지점 앞에 체크포인트가 없으면 아예 처음부터 다시 계산해, 이 차이가 30배(2 s 대 71 s)까지 벌어졌다. 바뀌는 상태는 별도 메시지로 대화 끝 쪽에 두고, 실제로 어디서 갈라지는지 서버 로그(`cached n_tokens`)로 한 번 확인하자.
